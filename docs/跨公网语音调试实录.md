# dsh-phone 跨公网语音调试实录（阶段 C/D）

> 记录 2026-08-20 跨设备语音（信令中继 + P2P 媒体）从「B 不来电」到「双端通话中」的完整排障过程。
> 这些 bug 每个都真实发生过、有现象、有根因、有修复，复现/迁移时直接对照本表。

对应版本：`@wwumit/dsh-phone` 0.5.0（GitHub wwumit/dsh-phone main，npm public）。
配套设计文档：`dsh-phone-跨公网语音设计.md`（架构/风险/回滚）。

---

## 0. 架构一句话

- 媒体：WebRTC P2P（音频不过服务器），STUN 打洞 `stun:compliancehub.cn:3478`（coturn 仅 STUN 模式，无 TURN）
- 信令：offer / answer / candidate 全部作为 `signal` 字段消息，走 registry 收件箱中继
  `POST /api/v1/phone/message`（投递到对端号码所属 agent 的 inbox）
  `GET /api/v1/phone/messages?did=...&since=<seq>`（增量轮询，5s）
- 双端共享同一个 agent DID（`did:cha2a:agent:dshlib`）与同一收件箱——这是后面所有「自回声」问题的根源

## 1. 四个真实 Bug（按发现顺序）

### Bug 1：信令没有发送者身份 → 主叫页自答回声

**现象**：主叫 A 拨号后，A 自己轮询收到自己发的 offer，且 `voiceRef.pc` 已存在 → 走「已接听自动应答」分支 → A 给自己发 answer，状态被搅乱。收件箱里 offer 重复（3 条），answer 却 0 条。

**根因**：
- 旧代码 `sendSignal` 发送 `fromNumber: '信令'`（占位符），收信端无法区分「自己发的」和「对端发的」
- `drainSignals` 过滤逻辑 `if (sig.to !== myNum && sig.to !== otherNum) continue` 放行了「发给对端号码」的消息，主叫页因此处理自己发给被叫的 offer

**修复**：
- 引入语音角色：`myRole`（'caller' | 'callee'）+ `myNumRef`（本端真实号码），拨号时置 caller，收到 offer 时置 callee
- `sendSignal` 带真实 `fromNumber`（本端号码），`to` 固定为对端号码
- `handleSignal` 过滤：`from && m.fromNumber === from && sig.type !== 'offer'` → 丢弃（answer/candidate 自回声）；offer 自回声保留（同页双面板靠它拿 pendingOffer）

### Bug 2：establishVoice 读过期 call 闭包 → 被叫误发 offer

**现象**：B 收到 offer 唤起来电 ✅，点接听 ✅，但 answer 永远发不出（信令 0 answer），A 侧不通话。

**根因**：`onAnswer` 先 `setCall(stage: 'connected')` 再调 `establishVoice()`，但 `establishVoice` 闭包里的 `call` 还是**本次渲染**的旧值（stage 仍为 'ringing'）→ 命中「主叫发 offer」分支（`stage==='ringing' && callerId==='A'`），B 作为被叫却发了一个 offer（甚至发给自己的号码）；`pendingOffer` 分支逻辑也被连带跳过。

**修复**：`establishVoice` 不再依赖 `call` 状态，改为按 `myRole` 分支：
- `myRole === 'caller'` → createOffer + setLocalDescription + send offer
- `else if (pendingOffer.current)` → setRemoteDescription + createAnswer + send answer

### Bug 3：浏览器 HTTP 缓存 → 新信令永远拉不到（最隐蔽）

**现象**：收件箱里明明有 offer（curl 能拉到），但页面轮询 `GET /phone/messages` 一直返回 0 msgs，B 不来电。

**根因**：
- registry `send()` 统一写 `Cache-Control: public, max-age=300`
- 浏览器 `fetch` 默认 `cache: 'default'` → 页面加载后第一次轮询（空收件箱）的响应被缓存；之后 POST 进 inbox 的新信令，同一 URL 的后续轮询**命中缓存**，永远返回旧的空响应
- 为什么隔离测试能过：offer 在页面加载**之前**就 POST 好了，首次轮询直接拉到，不触发缓存问题

**修复**（两端都要，缺一不可）：
- 服务端：messages 端点返回 `Cache-Control: no-store`（`send()` 加第 4 参 `extraHeaders` 覆盖默认头）
- 客户端：轮询 fetch 加 `cache: 'no-store'`

> 教训：轮询类 GET 端点必须显式禁用缓存；验证「新数据能否被拉到」要用「页面加载后再 POST」的时序，而不是「先 POST 再加载页面」。

### Bug 4：号码被 deactivate → answer 投递 404

**现象**：B 日志显示 `answer 已发送`（fetch 发出），但收件箱 0 answer，A 不通话。

**根因**：`POST /phone/message` 服务端校验 `pb.numbers.find(n => n.number === to && n.status === 'active')`；`+86951230001` 的 status 是 **deactivated**（早前测试时被注销过）→ answer 到 `+86951230001` 返回 404，消息不入库。

**修复**：号码簿里 `+86951230001` 重新置为 `active`。

> 教训：号码「能解析」不代表「能收消息」——投递校验看的是目标号码的 active 状态。测试前核对号码簿状态。

## 2. 次要加固（非阻塞，顺手修掉）

| 项 | 问题 | 修法 |
|---|---|---|
| candidate 时序 | candidate 先于 remoteDescription 到达 → `addIceCandidate` 抛 InvalidStateError 被吞，候选丢失 | `candBuf` ref 缓冲，remoteDescription 就绪（answer 分支 / establishVoice setRemoteDescription 后）再 `flushCandidates()` |
| answer 自回声 | 被叫收到自己发的 answer → `setRemoteDescription` InvalidStateError | `handleSignal` 丢弃 `m.fromNumber === myNumRef` 的 answer/candidate（Bug 1 修复的一部分） |
| 旧版信令 | 历史消息 `fromNumber: '信令'` 无身份 | `handleSignal` 直接忽略 `fromNumber === '信令'` 的消息 |

## 3. 验证方法（可复用）

环境：实验实例 `DSH_HOME=/Users/wuwei/Documents/DSH/.dsh-phone-test`，`pnpm dsh --profile test-phone --port 3099`（从 `/Users/wuwei/deepseek-harness` 目录启动，DSH_HOME 指向测试家目录）。

Playwright 双 context 模拟跨设备（两个独立浏览器 context，无共享 localStorage）：

```
1. 清空收件箱（ssh 服务器删 messages.json 里 inbox 各 did 的列表）
2. context A 打开面板 → 通讯录选号（避免手输号码格式问题）→ 拨号
3. context B 打开 B 面板 → 断言「来电」出现 → 点接听
4. 等待轮询 → 断言双端「通话中」状态
5. curl 收件箱统计信令：offer/answer/candidate 数量
```

关键断言：
- 信令完整性：`1 offer / 1 answer / ≥若干 candidate`，且无 `信令处理失败` console 错误
- B 侧必须出现「来电」UI（证明 offer 经中继唤起）
- 双端 `getByText(/语音|静音/)` 命中（证明 answer 回传 + 通话状态）

Playwright 启动参数（无头音频）：
```
chromium.launch({ args: ['--use-fake-ui-for-media-stream', '--use-fake-device-for-media-stream'] })
```

已验证结果（0.5.0）：
```
[A] 拨号 → offer 经中继 → [B] 来电 ✅
[B] 接听 → answer 回 A → 双方通话中 ✅✅
信令: 1 offer / 1 answer / 6 candidate（无报错）
```

测试脚本位置：`/tmp/verify-voice11.cjs`（含 ssh 清空收件箱 + 双 context 全流程；同目录有早期迭代 verify-voice2~10）。

## 4. 调试技巧备忘

- **隔离法定位**：跨设备不来电时，先「页面加载前 POST offer」→ B 能来电（链路通）；再「页面加载后 POST」→ B 不来电（暴露缓存 bug）。同一现象，两种时序，指向不同根因。
- **console 分段日志**：在 establishVoice 关键分支打 `[voice]` 前缀日志，验证后删除（保留 console.error 排障）。这次靠它确认「answer 已发送」——把「代码没走到」和「服务端没收」区分开。
- **收件箱污染**：每次验证前清空 inbox，否则旧 offer 会让新页面加载即处于来电状态（`view === 'dial' && !props.call` 导致拨号盘不显示，测试脚本找不到输入框）。
- **Playwright fill 陷阱**：受控输入框 `fill()` 可能不触发 React state 更新（target 仍为 '+86'，`dial()` 直接 return）。用通讯录选号（真实点击）或 `pressSequentially` 更稳。
- **号码格式**：注册表号码无空格（`+86951230001`），客户端常量需与之一致；早期消息里的 `+86 95123 0001`（带空格）是历史遗留。
